## 二、按问题（前后对比）

### P0-1 思考档位就近向下夹取 · `model_capabilities.py`

**问题**：Pro 系模型的合法档位是 `{low, medium, high}`（官方：MINIMAL 只有 Flash / Flash-Lite 有）。控制台选 `minimal` 时落进最后一行兜底，被抬成 `high`。

```python
# 原版
if level not in levels:
    level = "high" if "high" in levels else sorted(levels)[-1]   # ← 一律抬到最高

# 整改版
_LEVEL_ORDER = ["minimal", "low", "medium", "high"]

def _clamp_level(level, levels):
    """优先向下就近取，向下没有再向上。"""
    if level in levels: return level
    idx = _LEVEL_ORDER.index(level) if level in _LEVEL_ORDER else _LEVEL_ORDER.index("high")
    for i in range(idx, -1, -1):
        if _LEVEL_ORDER[i] in levels: return _LEVEL_ORDER[i]
    for i in range(idx + 1, len(_LEVEL_ORDER)):
        if _LEVEL_ORDER[i] in levels: return _LEVEL_ORDER[i]
    return sorted(levels)[0]
```

`resolve_thinking` 里三处（suppress 分支、off/none 归一、末尾校验）统一改用它。
顺带把 `capabilities_summary` 的档位排序从字典序（`high, low, medium, minimal`）改成强度序。

**效果对照**：

| 模型 | 模式 | 控制台档位 | 原版 | 整改版 |
|---|---|---|---|---|
| `gemini-3.1-pro-preview` | console | minimal | **high** ❌ | **low** ✅ |
| `gemini-3.1-pro-preview` | off | — | low | low |
| `gemini-3.6-flash` | console | minimal | minimal | minimal |

### P0-2 `retry_max` 语义统一 · `api_helpers.py`

**问题**：Express 通道写成 `range(retry_max)`，把"重试次数"当成"总尝试次数"。`retry_max=0` 时循环体一次都不执行，非流式 `response_obj_call` 保持 `None` 后抛一条误导性的"无有效内容"，真流式只吐一个心跳就关流（连 `[DONE]` 都没有）。Cookie 通道用的是 `range(retry_max + 1)`，两边语义不一致。

```python
# 原版（两处）
try:
    max_retries = int(app_state.get_setting("retry_max", 20))
except (TypeError, ValueError):
    max_retries = 20
for attempt in range(max_retries):
    ...
    if is_retryable and attempt < max_retries - 1:

# 整改版
def get_retry_settings() -> tuple[int, float]:
    """retry_max = 失败后的重试次数，总请求次数 = retry_max + 1。钳到 0–50 / 0–120s。"""

max_retries, backoff = get_retry_settings()
for attempt in range(max_retries + 1):
    ...
    if is_retryable and attempt < max_retries:

# 循环后新增兜底，不让 None 流到有效性检查
if response_obj_call is None:
    return JSONResponse(status_code=502, content=create_openai_error_response(
        502, "上游未返回任何响应（重试已耗尽）。", "upstream_error"))
```

Cookie 通道也改为复用 `get_retry_settings()`，删掉了自己那份 `MAX_RETRIES` / `RETRY_BACKOFF` 常量。

### P0-3 流式并行函数调用 · `api_helpers.py`

**问题**：遍历 parts 时遇到第一个 `function_call` 就 `break`，其余并行调用被丢弃；`delta.tool_calls[].index` 硬编码为 0，客户端会把多个调用合并成一个。官方要求并行调用必须完整按 `FC1,FC2,FR1,FR2` 回传，缺一个就 400。

```python
# 原版
for part in candidate.content.parts:
    if part.function_call is not None:
        ...
        current_tool_call_delta = {"index": 0, ...}   # ← 恒为 0
        ...
        break                                          # ← 只取第一个

# 整改版
class ToolCallIndexer:
    """一次流式响应内按 (candidate, 出现顺序) 分配稳定序号。
    并行调用可能分布在不同 chunk，序号必须由调用方持有；每次重试新建实例。"""

tool_call_deltas = []
for part in candidate.content.parts:
    fc = getattr(part, "function_call", None)
    if fc is None: continue
    tool_call_deltas.append({
        "index": indexer.next_index(candidate_index) if indexer else len(tool_call_deltas),
        "id": build_tool_call_id(fc, part, embed_sig),
        ...
    })
```

真流式生成器在每次 attempt 开始处新建 `ToolCallIndexer()` 并传入。

### P0-4 思考签名运输 · `signature_store.py`（新）+ `message_processing.py`

**问题**：base64 签名直接拼进 `tool_call_id`（`{id}__thought__{base64}`）。签名通常几百到上千字符，许多前端对 `tool_call_id` 有长度限制或会截断，截断后回传解不出签名 → Gemini 3 直接 400，且没有任何降级路径。此外 `api_helpers` 与 `message_processing` 各有一份复制粘贴的实现，已出现细微不一致（一个用 `response_id`、一个用 `base_id` 拼 fallback id）。

**四层设计**：

| 层 | 做法 |
|---|---|
| 1 主路径 | 短 id（`call_` + 16 位 hex，共 21 字符）+ 进程内 TTL LRU 缓存（2h / 5000 条） |
| 2 兼容 | 仍解析旧的 `__thought__` 内嵌格式；控制台开关 `embed_thought_signature_in_id` 可退回旧格式（多副本部署用） |
| 3 降级 | 取不回签名且模型是 3.x 时，用官方 `skip_thought_signature_validator` 哨兵，保证请求不 400 |
| 4 顺序 | 修掉同角色合并把文本 part 插进连续 function call 之间的问题 |

第 4 层的具体改动：

```python
# 原版：无条件插入分隔符
if merged[-1].role == msg.role:
    merged[-1].parts.append(types.Part.from_text(text="\n\n"))
    merged[-1].parts.extend(msg.parts)

# 整改版：只有两侧都是纯文本时才插
if _is_text_only(merged[-1]) and _is_text_only(msg):
    merged[-1].parts.append(types.Part.from_text(text="\n\n"))
merged[-1].parts.extend(msg.parts)
```

`create_gemini_prompt(messages, model_name="")` 新增第二参数，Express 通道用 `functools.partial` 传入真实模型名，用于判断是否需要哨兵（仅 3.x 强校验）。

**已知局限**（写进了 README）：纯文本轮次的签名在 OpenAI 协议里无处安放，注定丢失。官方说纯文本不强校验，只影响质量。

### P1-2 两条通道共用内容转换 · `message_processing.py` + `cookie_proxy.py`

**问题**：README 把"输入图压缩"描述成全局设置，实际 `optimize_image_bytes` 只在 Express 路径调用。Cookie 通道还有两个缺口：只认 `data:` URL（`http(s)://` 图片被静默丢弃）、不解析正文里的 markdown data-URL（多轮修图时上一张图被当成巨大纯文本发出）。

新增 `openai_content_to_wire_parts(content)`：返回 batchGraphql 的 camelCase parts，内部复用 `optimize_image_bytes` 与 `_extract_markdown_images_to_parts`，Cookie 通道改为调用它。

同时把**同步阻塞的转换搬出事件循环**：

```python
# Express
actual_prompt_for_call = await asyncio.to_thread(prompt_func, request_obj.messages)
# Cookie
body = await build_batch_graphql_body_async(project_id, model, request_obj, prefill_active)
```

原版在 async 路径上用 `ThreadPoolExecutor(...).result(timeout=12)` 阻塞等待，实际会卡住整个事件循环。

### P1-4 状态管理器 · `runtime_state.py`（重写）

| 项 | 原版 | 整改版 |
|---|---|---|
| 读取 | 每个 getter 都 `_load_state()` 同步读盘 | 内存优先，只在启动 / `reload()` 时读盘 |

原版全项目有 20+ 处设置读取，全在 async 请求路径上（每压缩一张图片还要再读一次），高并发下会把事件循环串行化。
