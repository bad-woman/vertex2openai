## 1. P0 — 必须优先修

### P0-1 `native_thinking_mode=console` 在 Pro 模型上反向放大思考

**现象**：控制台把"思考强度"设为 `minimal` 并选"强制用上方档位"，对 `gemini-3.1-pro-preview` 实测得到 `thinkingLevel=HIGH`。用户选最低档，拿到最高档——正好是这个项目最想解决的问题的反面。

**根因**（`model_capabilities.py:236-241`）：

```python
level = req_effort or settings.get("thinking_g3_level") or prof.get("default_level", "high")
level = str(level).lower()
if level in ("off", "none"):
    level = "minimal" if "minimal" in levels else "low"
if level not in levels:
    level = "high" if "high" in levels else sorted(levels)[-1]   # ← 非法档位一律兜底到 high
```

Pro 的合法档位是 `{low, medium, high}`（官方：MINIMAL 只有 Flash / Flash-Lite 有），`minimal` 落进最后一行被抬成 `high`。`suppress` 分支（第 234 行）兜底到 `low` 是对的，只有 `console` 分支错。

**修改思路**：引入有序档位阶梯，统一"向下就近夹取"，两条分支共用：

```python
_LEVEL_ORDER = ["minimal", "low", "medium", "high"]

def _clamp_level(level: str, levels: set) -> str:
    """把任意档位夹到该模型合法档位；优先向下取最接近的，没有再向上。"""
    if level in levels:
        return level
    try:
        idx = _LEVEL_ORDER.index(level)
    except ValueError:
        idx = _LEVEL_ORDER.index("high")      # 未知词按最高处理，再向下夹
    for i in range(idx, -1, -1):              # 先向下
        if _LEVEL_ORDER[i] in levels:
            return _LEVEL_ORDER[i]
    for i in range(idx + 1, len(_LEVEL_ORDER)):   # 兜底向上
        if _LEVEL_ORDER[i] in levels:
            return _LEVEL_ORDER[i]
    return sorted(levels)[0]
```

`resolve_thinking` 里三处改为：

- suppress 分支：`level = _clamp_level("minimal", levels)`
- `off`/`none` 归一：`level = _clamp_level("minimal", levels)`
- 末尾校验：`level = _clamp_level(level, levels)`

**验证**：`(pro, console, minimal) → low`、`(pro, console, medium) → medium`、`(flash, console, minimal) → minimal`、`(pro, request, xhigh) → high`。

**注意**：`_LEVEL_ORDER` 要和 `capabilities_summary` 里给前端的 `sorted(levels)` 对齐——前端目前用字典序排序（`high, low, medium, minimal`），显示顺序是乱的，顺手改成按 `_LEVEL_ORDER` 排。

### P0-2 `retry_max=0` 使 Express 通道完全失效

**现象**：控制台把重试次数设成 0，Express 通道非流式返回一条误导性的"无有效内容"，真流式只吐一个心跳就关流，连 `data: [DONE]` 都没有。

**根因**：Express 用 `for attempt in range(max_retries)`（`api_helpers.py:701` 与 `808`），把"重试次数"当成了"总尝试次数"；Cookie 通道用的是 `range(retry_max + 1)`，语义不一致。`max_retries=0` 时循环体一次都不执行，`response_obj_call` 保持 `None` 落到 `is_gemini_response_valid(None)`。

**修改思路**：

1. 在 `config.py` 注释里写死语义：**`retry_max` = 失败后的重试次数，总请求次数 = `retry_max + 1`**。
2. 两处循环改为 `range(max_retries + 1)`，并把内部的续判条件同步 `-1`：
   - 流式：`if is_retryable and not has_yielded and attempt < max_retries - 1:` → `attempt < max_retries`
   - 非流式：`if is_retryable_exception(e_call) and attempt < max_retries - 1:` → `attempt < max_retries`
3. 读取时钳位：`max_retries = max(0, int(app_state.get_setting("retry_max", 10)))`，默认值也从 20 统一为 `DEFAULT_SETTINGS` 的 10。
4. 循环后加显式兜底，不要让 `None` 流到下游：

```python
if response_obj_call is None:
    return JSONResponse(status_code=502, content=create_openai_error_response(
        502, "上游未返回任何响应（重试已耗尽）。", "upstream_error"))
```

5. 控制台侧给 `retry_max` 加输入校验（0–50 整数）。

**验证**：`retry_max=0` 时非流式返回一次真实结果或真实错误码；真流式正常输出并以 `[DONE]` 收尾。

### P0-3 流式并行函数调用被丢弃

**现象**：模型一次返回多个并行 function call 时，只有第一个能到达客户端。

**根因**（`api_helpers.py:398-426`）：遍历 parts 时遇到第一个 `function_call` 就 `break`；且 delta 里 `"index": 0` 是硬编码。OpenAI 客户端按 `index` 累积 tool_calls，所有调用都是 0 会被合并成一个。非流式路径（`message_processing.py:process_gemini_response_to_openai_dict`）是正确的，只有流式有此问题。

这条同时牵涉官方的顺序约束：并行调用返回 `FC1+签名, FC2` 时，回传必须是 `FC1+签名, FC2, FR1, FR2`，交错成 `FC1, FR1, FC2, FR2` 会 400。丢掉 FC2 会直接违反这个约束。

**修改思路**：

1. 去掉 `break`，改为遍历全部 parts，收集所有 `function_call`。
2. 引入跨 chunk 稳定的序号器。因为流式下并行调用可能分布在不同 chunk，序号必须由调用方持有：

```python
class ToolCallIndexer:
    """一次流式响应内，按 (candidate_index, 出现顺序) 分配稳定的 tool_calls index。"""
    def __init__(self):
        self._next = {}          # candidate_index -> 下一个可用序号
    def next_index(self, candidate_index: int) -> int:
        i = self._next.get(candidate_index, 0)
        self._next[candidate_index] = i + 1
        return i
```

3. `convert_chunk_to_openai(chunk, model, response_id, candidate_index, indexer=None)` 增加参数；`_gemini_real_stream_generator_inner` 在**每次 attempt 开始时**新建一个 `ToolCallIndexer`（重试会重发整轮，序号必须重置）。
4. `delta_payload["content"] = None` 只在确实有 tool_call 时设置一次，不要在循环里反复覆盖。

**验证**：构造一个返回两个并行 function call 的 mock chunk，断言 SSE 中出现 `index: 0` 与 `index: 1` 两条、id 不同；再断言两条 tool 结果按 FC1、FC2、FR1、FR2 的顺序被 `create_gemini_prompt` 还原。

### P0-4 思考签名（thought signature）的运输方式不可靠

**现象/风险**：签名以 `{id}__thought__{base64}` 塞进 `tool_call_id`。base64 签名通常几百到上千字符，很多前端对 `tool_call_id` 有长度限制或会截断；一旦截断，回传时解不出签名，Gemini 3 直接 400（函数调用是强校验）。目前没有任何降级路径。

**官方约束回顾**：

- 签名可以出现在任意 part（text、functionCall）上；函数调用强校验，缺失即 400；纯文本不强校验但会降低质量。
- Gemini 3 的签名总在**第一个** function call part 上，必须原样回传。
- 确实拿不到签名时，可把 `thought_signature` 设为 `skip_thought_signature_validator` 跳过校验，官方明确这是最后手段、会损害性能。

**修改思路**（三层，逐层降级）：

**第一层 — 短 id + 服务端旁路缓存（主路径）**

不再把签名塞进 id。生成 ≤40 字符的短 id（`call_` + 12 位 hex），把签名存进进程内 TTL LRU：

```python
# 新文件 app/signature_store.py
class SignatureStore:
    """tool_call_id -> thought_signature 的短期缓存（默认 2h / 5000 条）。
    仅在同一进程内有效；跨进程或重启后由第二/三层兜底。"""
    def put(self, call_id: str, sig: bytes) -> None: ...
    def get(self, call_id: str) -> bytes | None: ...
```

`api_helpers.convert_chunk_to_openai` 与 `message_processing.process_gemini_response_to_openai_dict` 里两处生成 id 的逻辑合并成一个公共函数（现在是复制粘贴的两份，已经出现过不一致），出站时 `store.put()`；`create_gemini_prompt` 解析 tool 消息时先 `store.get()`。

**第二层 — 兼容旧的 `__thought__` 形式**

保留解析逻辑，让升级前发出的历史仍能工作；但**不再生成**这种 id。可在控制台加一个开关 `embed_thought_signature_in_id`（默认关）给确有跨进程需求的人用。

**第三层 — 哨兵降级，绝不让请求整体失败**

缓存未命中且 id 里也没有签名时，不要发一个裸 function_call：

```python
if thought_sig_bytes is None and profile["family"] == "g3":
    thought_sig_bytes = b"skip_thought_signature_validator"
    print("⚠️ [工具调用] 未能恢复思考签名，已使用官方跳过校验哨兵（会降低模型表现）。")
```

**第四层 — 修掉会破坏 part 顺序的合并逻辑**

`create_gemini_prompt` 末尾的同角色合并会插入 `Part.from_text("\n\n")`。若两个连续的 model 轮次都带 function call，这个文本 part 会插到 FC 之间，可能触发 `Malformed_Function_Call` 或签名校验失败。改为**只有两侧都是纯文本 part 时才插分隔符**：

```python
def _is_text_only(content) -> bool:
    return all(getattr(p, "text", None) is not None for p in content.parts)

if merged and merged[-1].role == msg.role:
    if _is_text_only(merged[-1]) and _is_text_only(msg):
        merged[-1].parts.append(types.Part.from_text(text="\n\n"))
    merged[-1].parts.extend(msg.parts)
```

**文本 part 的签名怎么办**：OpenAI 协议里没有地方挂它，纯文本轮次的签名注定丢失。官方说纯文本不强校验，只影响质量。**不要为此发明协议扩展**，在 README 的"已知限制"里写清楚即可。

**验证**：单测覆盖——短 id 长度 ≤40；缓存命中时签名字节完全一致；缓存未命中时降级为哨兵且不抛异常；旧 `__thought__` id 仍能解析；两个连续 model 轮次带 FC 时不插入文本 part。

## 2. P1 — 影响正确性/性能，第二批修

### P1-1 Cookie 通道静默破坏工具历史

`cookie_proxy.py:157` 的 `gemini_role = "user" if role == "user" else "model"` 把 `role="tool"` 变成 model 轮次，assistant 的 `tool_calls` 字段则被完全忽略。既然该通道本就不下发 `functionDeclarations`，**应该在入口显式拒绝**而不是发出一段语义错乱的历史：

```python
if request_obj.tools or any(getattr(m, "tool_calls", None) or m.role == "tool"
                            for m in request_obj.messages):
    return JSONResponse(status_code=400, content={"error": {
        "message": "Cookie 直连通道暂不支持函数调用，请切换到标准（Express）模式。",
        "type": "unsupported_feature"}})
```

同时把 `system` 之外的未知 role 也显式处理，别一律折成 model。

### P1-2 Cookie 通道的图片处理与 Express 不一致

README 把"输入图压缩"描述成控制台全局项，实际 `optimize_image_bytes` 只在 `message_processing.py` 的 Express 路径调用。Cookie 通道还有两个缺口：只认 `data:` URL（`http(s)://` 图片被静默丢弃）、不解析正文里的 markdown data-URL 图片（多轮修图时上一张图会被当成巨大的纯文本发出去）。

**思路**：把 Express 侧的图片处理抽成通道无关的工具函数（`extract_parts_from_openai_content(content) -> list[dict]`，返回 batchGraphql 的 camelCase part 结构），两个通道共用；远程图片抓取顺便改成 `httpx.AsyncClient`（见下）。

### P1-3 OpenAI 字段兼容

```python
stop: str | list[str] | None = None        # OpenAI 允许字符串
top_logprobs: int | None = None            # 新增，对应 OpenAI 语义
logprobs: bool | int | None = None         # 收下 bool，内部再规范化
```

在 `create_generation_config` 里统一规范化：`stop` 一律转 list；`logprobs=True` 映射为 `response_logprobs=True` + `logprobs=top_logprobs or 1`。Cookie 通道那句 `if isinstance(request.stop, list) else [request.stop]` 就可以删掉了。

### P1-4 `runtime_state` 的读盘与原子写

全项目有 26 处 `get_settings/get_setting/get_effective_settings` 调用，每次都 `_load_state()` 同步读盘并持 `threading.Lock`，而这些调用全在 async 请求路径上（每张图片压缩也调一次）。

**思路**：

- 内存为准 + 写时落盘：`_load_state` 只在 `__init__` 和显式 `reload()` 时读盘；所有 setter 改内存 + `_save_state`。
- 原子写：`tempfile.NamedTemporaryFile(dir=同目录)` + `os.replace()`。
- `get_settings()` 返回深拷贝（现在 `merged.update(current)` 是浅拷贝，`model_overrides` 这层嵌套字典会被调用方意外改到）。
- 若未来上多 worker，改用文件锁或干脆约束单 worker，并在 README 注明。

### P1-5 `logger.py` 的三个隐患

1. **全局劫持 `builtins.print`**：影响所有第三方库输出。改为标准 `logging` + 自定义 Handler，业务代码逐步从 `print` 迁到 `log.info`（可以先加 Handler、保留 print 兼容，分两步走）。
2. **跨线程操作 `asyncio.Queue`**：`push()` 可能从任意线程被调用，`put_nowait` 与遍历 `self.queues` 都不是线程安全的。改成 `loop.call_soon_threadsafe(q.put_nowait, msg)`，并给 `queues` 加锁或换 `collections.deque` 快照遍历；队列要设 `maxsize` 防止慢客户端撑爆内存。
3. **正则反解 token**：`re.search(r'提示词:\s*(\d+).*?思考与生成:\s*(\d+)')` 与日志文案强耦合，改一句中文就静默失效。改为在产生 usage 的地方直接调 `stats.add_tokens(p, c)`，日志只负责打印。

顺带统一统计口径：`stats_tracker_middleware`（`main.py:52`）只按 HTTP 状态码计错，而流式响应先返回 200、错误发生在 body 里，所以 Express 流式的失败从不计入。要么在两个通道的流式收尾处统一 `add_success/add_error`（Cookie 通道已经这么做了），要么给中间件加一个"由通道回填"的机制。

### P1-6 假流式忽略控制台重试设置

`gemini_fake_stream_generator` 走 `execute_with_retry`（tenacity，`stop_after_attempt(20)` 硬编码）。改为复用与真流式相同的手写退避循环，读 `retry_max`/`retry_backoff_seconds`，并在等待期间继续吐 keep-alive、检测客户端断开（目前假流式路径完全没有断连检测）。改完 `execute_with_retry` 与 `tenacity` 依赖就可以一起删掉。

### P1-7 2.5 Flash-Lite 预算下限

`model_capabilities.py:131` 把所有非 pro 的 2.5 都按 `budget_min=0` 处理。官方：2.5 Flash-Lite 范围 512–24576（0 表示关闭）。

```python
if is_pro:
    budget_min, budget_max, can_zero = 128, 32768, False
elif "flash-lite" in name:
    budget_min, budget_max, can_zero = 512, 24576, True    # 0=关闭，非 0 最低 512
else:
    budget_min, budget_max, can_zero = 0, 24576, True
```

夹取逻辑要放行 `0`：`if budget != -1 and budget != 0: budget = max(bmin, min(bmax, budget))`。

### P1-8 Express 流式缺 usage

Cookie 通道实现了 `stream_options.include_usage` 与 `_make_usage_chunk`，Express 流式一个 usage 块都不发（客户端只能看到 0）。把 `_wants_usage` 和 `_make_usage_chunk` 提到公共模块，Express 真流式在 `[DONE]` 前按需补一个 usage 块。假流式路径同理。

### P1-9 生图丢弃 system_instruction

`api_helpers.py:215` 的 `if system_texts and "image" not in request.model.lower()` 没有注释理由。Gemini 3 生图模型是支持系统指令的。**思路**：先做一次真机验证，若可用则去掉这个条件；若确有问题，把注释补上（写清是哪个模型、什么报错），别留裸判断。

## 4. 文档整改

### D-1 删掉 README 里 JAILBREAK 的错误因果（最重要）

README 现在写"缺少该分类时…越狱过滤器拦掉了正文而思考照常流出"。官方文档明确：**越狱分类器默认关闭**，要打开必须显式把 JAILBREAK 阈值设为具体的拦截值。所以"不下发该分类"不会启用任何过滤，下发 `OFF` 也只是 no-op。

而且 HANDOFF 第四轮已经自己推翻了这个结论（改判为 HIGH 档思考跑飞/被截断），两份文档目前互相矛盾。

**改法**：README 保留"两通道下发同一套 safety 设置以保持一致"这个事实，删掉因果句，把"有思考无正文"的解释统一指向 HANDOFF 的定论（前端恒发 `xhigh` → 思考跑飞）。HANDOFF 第四节里旧的 JAILBREAK 结论也加一行"已被第四轮推翻"。

顺带统一两个通道的阈值：Express 用 `BLOCK_NONE`、Cookie 用 `OFF`，两者语义不同（`OFF` 是彻底关闭过滤器，`BLOCK_NONE` 是不拦截但仍返回评分）。既然有 `SAFETY_SCORE` 显示功能依赖 safety_ratings，建议统一为 `OFF` 或统一为 `BLOCK_NONE` 并在 README 说明取舍。

### D-2 更新 Interactions API 的描述

现状描述"Agent Platform 尚未对基础 Gemini 模型开放 Interactions（仅少数 agent）"不准确。准确表述：

- Gemini API（ai.google.dev）侧：Interactions API 已于 2026-06 GA 并被推荐用于新项目，`generateContent` 被称为 legacy 但继续完整支持。
- Agent Platform 侧：Interactions API 仍标注为 **experimental**，覆盖平台上托管的生成式模型与 agent。
- Express 模式的 REST 面只有 `countTokens` / `generateContent` / `streamGenerateContent`——**这才是本项目暂不迁移的真正理由**，写这个比写"只对 agent 开放"更站得住。

## 5. 安全与合规

### S-1 凭证保护

`web_state.json` 明文保存整条 Google 会话 Cookie（含 `__Secure-1PSID` 等），等价于该 Google 账号的完整访问权。而 README 顶部是 HuggingFace Space 的 front-matter——**公开 Space + 默认口令 `123456` + 明文 Cookie** 是很危险的组合。

**分层处理**：

1. 启动时若 `API_KEY` 为默认值：打红色告警；若同时检测到 `SPACE_ID` 等公开托管环境变量，直接拒绝启动。
2. Cookie 至少做一层本地加密（用 `API_KEY` 派生密钥，`cryptography.fernet`），落盘存密文。这挡不住能读环境变量的人，但能挡住误提交/误挂载/快照泄漏。
3. `/api/settings/runtime` 现在会把完整 Cookie 明文回吐给前端，改成只返回掩码（`SAPISID=abc…xyz` 形式）+ 一个"是否已配置"的布尔。
4. 文件权限 `os.chmod(STATE_FILE, 0o600)`。

### S-2 条款与稳定性提示

Cookie 直连模式是用硬编码的 Web 客户端 key + 固定 `querySignature`（`cookie_auth.py`）冒充 Cloud Console 前端调用私有 `batchGraphql`。README 现在把"规避 429 限流"当卖点写，等于把风险描述成了功能。

**改法**：在 Cookie 模式章节开头加一段风险提示，如实说明——该接口不受任何兼容性承诺保护（Google 改一次 `querySignature` 即全线失效）、自动化调用可能与 Google Cloud 使用条款相冲突、存在账号被处置的风险，建议仅用自有账号、自担风险。同时把"规避限流"的表述改成中性的"走网页端配额"。

### S-3 数据持久化

`docker-compose.yml` 没有卷，`up --force-recreate` 或升级镜像后 `web_state.json` 就没了，Cookie 和全部控制台设置要重配。

```yaml
    volumes:
      - ./data:/app/data
    environment:
      - STATE_DIR=/app/data
```

配合把 `runtime_state.STATE_FILE` 改为读 `STATE_DIR` 环境变量（默认当前目录，保持向后兼容）。

## 6. 能力矩阵的长期维护策略

这是项目最有价值的部分，值得单独定个规矩，避免下次又靠"真机试出来"：

1. **每条白名单/阈值都带出处注释**：`# 官方: <文档名>，核对于 2026-07-26`。现在 `model_capabilities.py` 顶部有一段总的依据说明，但具体常量（比例、分辨率、预算区间）没有逐条溯源，出错时无法判断是抄错还是文档变了。
2. **前向安全的默认值保持不变**：未知/未来型号按"最新代"处理（移除弃用采样参数、走预填充兼容）这个设计是对的，继续保持。
3. **加一个 `-latest` 别名的例外**：`gemini-flash-latest` 现在被当作最新代处理（temperature 被剥离），但它实际指向 `gemini-3.5-flash`（该模型仍接受 temperature）。方向是安全的（只是少发参数），但可以在 `_temp_deprecated` 里加一张小的别名映射表，或者在 README 注明"别名模型按最保守策略处理"。
4. **写一个 `scripts/check_models.py`**：读 `vertexModels.json`，逐个打印 `capabilities_summary`，人工比对官方文档。每次官方发新模型时跑一遍，比翻代码快。
