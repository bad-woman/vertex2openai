# 实机验证清单

**用法**：按 A → B → C → D 四组推进，每组按凭证可得性分层。每项都写了「操作 / 预期 / 判定失败」。
所有 `PROXY` 请替换为你的服务地址（默认 `http://localhost:8050`），`KEY` 替换为 `API_KEY`。

> **验证前必做**：控制台 → 模型参数 → 打开 **「出站参数调试日志」**（`debug_outbound`）。
> 不开这个开关，A/B 组里大部分思考档位相关的项无法直接观察。

## B 组 · 需要 Express API Key

> 前置：控制台切到「标准模式」，配好 `VERTEX_EXPRESS_API_KEY`，打开出站调试日志。

### B-1 【P0-1】Pro 模型档位不再被抬高 ★核心

1. 控制台 → 模型参数 → 选 `gemini-3.1-pro-preview`
2. 原生思考控制 → **强制用上方档位**；思考强度 → **minimal**
3. 保存为该模型专属
4. 发一条请求（故意带上前端常发的 `xhigh`）：

```bash
curl PROXY/v1/chat/completions -H "Authorization: Bearer KEY" \
  -H "Content-Type: application/json" -d '{
    "model":"gemini-3.1-pro-preview",
    "messages":[{"role":"user","content":"用三句话解释相对论"}],
    "reasoning_effort":"xhigh"
  }'
```

- **预期日志**：`thinkingConfig={'include_thoughts': True, 'thinking_level': 'low'}`
- **失败判定**：出现 `'thinking_level': 'high'` → P0-1 未生效（这正是原版的 bug）
- **对照**：把模型换成 `gemini-3.6-flash` 重做，应得到 `'minimal'`

### B-2 【P0-2】retry_max=0 仍会发请求 ★核心

1. 控制台 → 重试次数设为 **0** → 保存
2. 分别发非流式与流式请求：

```bash
curl PROXY/v1/chat/completions -H "Authorization: Bearer KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"gemini-3.6-flash","messages":[{"role":"user","content":"hi"}]}'

curl -N PROXY/v1/chat/completions -H "Authorization: Bearer KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"gemini-3.6-flash","messages":[{"role":"user","content":"hi"}],"stream":true}'
```

- **预期**：都返回正常内容；流式以 `data: [DONE]` 收尾
- **失败判定**：非流式返回"无有效内容"、流式只有一个 `: keep-alive` 就断 → 未生效
- 验证完记得把重试次数改回 10

### B-3 【P1-7】2.5 Flash-Lite 预算下限

```bash
curl PROXY/v1/chat/completions -H "Authorization: Bearer KEY" \
  -H "Content-Type: application/json" -d '{
    "model":"gemini-2.5-flash-lite",
    "messages":[{"role":"user","content":"hi"}],
    "thinking_budget":100
  }'
```

- **预期日志**：`thinkingConfig={... 'thinking_budget': 512}`（被抬到合法下限）
- 再传 `"thinking_budget":0` → 应为 `0`（关闭思考，**不能**被抬成 512）
- **注意**：该模型可能不在你的项目/区域内，404 属正常，换 `gemini-2.5-flash` 观察 0 是否保持为 0

### B-4 【P1-3】OpenAI 字段兼容

```bash
# stop 传字符串（原版会 422）
curl PROXY/v1/chat/completions -H "Authorization: Bearer KEY" \
  -H "Content-Type: application/json" \

# logprobs 传 bool（OpenAI 语义）
```

- **预期**：都返回 200；日志中 `stop_sequences=['5']`
- **失败**：422 Unprocessable Entity → 未生效

### B-5 【P0-3】并行函数调用 ★改动面最大

用一个会触发多个工具的提示：

```bash
curl -N PROXY/v1/chat/completions -H "Authorization: Bearer KEY" \
  -H "Content-Type: application/json" -d '{
    "model":"gemini-3.6-flash","stream":true,
    "messages":[{"role":"user","content":"同时查一下东京和巴黎现在的天气"}],
    "tools":[{"type":"function","function":{"name":"get_weather",
      "description":"查询城市天气",
      "parameters":{"type":"object","properties":{"city":{"type":"string"}},"required":["city"]}}}]
  }'
```

- **预期**：SSE 里出现**两个** `tool_calls` 条目，`index` 分别为 `0` 和 `1`，`id` 不同
- **失败判定**：只有一个调用，或两个都是 `index: 0` → P0-3 未生效
- 非流式（去掉 `"stream":true`）做同样检查

### B-6 【P0-4】多轮工具往返与思考签名 ★风险最高

延续 B-5，把模型返回的 `tool_calls` 原样回传，附上工具结果，发第二轮：

```bash
curl PROXY/v1/chat/completions -H "Authorization: Bearer KEY" \
  -H "Content-Type: application/json" -d '{
    "model":"gemini-3.6-flash",
    "messages":[
      {"role":"user","content":"东京天气如何"},
      {"role":"assistant","content":null,"tool_calls":[{"id":"<上一轮返回的id>",
        "type":"function","function":{"name":"get_weather","arguments":"{\"city\":\"Tokyo\"}"}}]},
      {"role":"tool","tool_call_id":"<同一个id>","name":"get_weather","content":"{\"temp\":28}"}
    ],
    "tools":[{"type":"function","function":{"name":"get_weather",
      "parameters":{"type":"object","properties":{"city":{"type":"string"}}}}}]
  }'
```

- **检查点 1**：上一轮返回的 `tool_calls[].id` **长度应 ≤ 40 字符**，且不含 `__thought__`
- **检查点 2**：第二轮返回 200 且内容合理，**没有** `missing a thought_signature` 的 400
- **检查点 3**：日志里**不应**出现 `⚠️ [工具调用] 未能恢复思考签名…` —— 出现说明缓存没命中，虽然会用哨兵兜住不报错，但模型表现会下降，需要排查
- **补充测试**：重启服务后再发第二轮（模拟缓存丢失），此时**应该**看到那条哨兵警告，且请求**仍然成功**——这验证的是第三层降级
- **多副本部署的话**：把「思考签名内嵌 tool_call_id」开关打开再测一遍

### B-7 【P1-8】流式 usage


### B-9 【P1-6】假流式的重试与断连

1. 控制台打开「假流式」
2. 发流式请求后**立刻 Ctrl+C 断开**

## C 组 · 需要 Google Cookie

> 前置：控制台切到「Cookie 直连反代」，配好 Cookie 与 Project ID。

### C-1 【S-1】Cookie 掩码与"留空保持不变" ★易踩坑

1. 保存 Cookie 后**刷新页面**
2. **预期**：Cookie 输入框是**空的**，placeholder 显示 `已配置：xxx…xxxx（共 N 个 cookie 字段，M 字符）`
3. 只改 Project ID（Cookie 框留空）→ 点保存
4. **预期**：提示 `✅ 已保留原有 Cookie，仅更新 Project ID。`，随后发请求仍能正常工作
- **失败判定**：若保存后 Cookie 失效，说明掩码被当成真 Cookie 写回了 —— 这是本次改动里最需要确认的回归点

### C-2 【P1-1】工具流量被明确拒绝

```bash
curl PROXY/v1/chat/completions -H "Authorization: Bearer KEY" \
  -H "Content-Type: application/json" -d '{
    "model":"gemini-3.6-flash",
    "messages":[{"role":"user","content":"hi"}],
    "tools":[{"type":"function","function":{"name":"f","parameters":{"type":"object"}}}]

```

- **预期**：HTTP **400**，消息含"Cookie 直连通道暂不支持函数调用"
- **失败**：返回 200 但内容错乱 → 未生效

### C-3 【P1-2】图片处理与 Express 对齐

分别测三种输入：

1. `data:` URL 内联图 → 应正常识别
2. `http(s)://` 远程图 → **原版会静默丢弃**，现在应能识别
3. 正文里带 markdown data-URL 图（模拟多轮修图）→ 应被抽成图片 part 而非巨大文本

- **配合**：控制台把「输入图压缩」开关关掉再测一次，确认开关对 Cookie 通道**也生效**了

### C-4 【文本保真】缩进不再被压平 ★本次新发现的问题

```bash
curl PROXY/v1/chat/completions -H "Authorization: Bearer KEY" \
  -H "Content-Type: application/json" -d '{
    "model":"gemini-3.6-flash",
    "messages":[{"role":"user","content":"原样重复下面内容：\ndef f():\n    return  1"}]
  }'
```

- **预期**：模型看到的是保留缩进和双空格的原文
- **背景**：原版对**所有**消息执行 `re.sub(r"[ \t]+", " ", ...)`，代码块 / ASCII 图 / 酒馆预设排版都会被静默压平。这个问题 Express 通道也有

### C-5 生图分辨率与比例

```bash
curl PROXY/v1/chat/completions -H "Authorization: Bearer KEY" \
  -H "Content-Type: application/json" -d '{
    "model":"gemini-3.1-flash-image",
    "messages":[{"role":"user","content":"一只赛博朋克猫"}],
    "image_size":"512","aspect_ratio":"1:8"
  }'
```

- **预期**：`imageConfig={'imageSize': '512', 'aspectRatio': '1:8'}`，返回图片
- 再用 `gemini-3-pro-image` + `image_size:"512"` → 应**回退为 `1K`**（pro 不支持 512）
- 用 `aspect_ratio:"9:21"` → 应**不下发**该字段（已从白名单移除），由模型自行决定，不报错

### C-6 【P0-1 在 Cookie 通道】思考剥离

对 `gemini-3.6-flash` 设「关闭原生思考」，发一条重预设请求：

- **预期日志**：`thinkingConfig={'thinkingLevel': 'MINIMAL', 'includeThoughts': False}`
- **预期响应**：`reasoning_content` 为空（batchGraphql 忽略 `includeThoughts`，由本代理在响应侧剥离）
- 这条是原版就有的行为，属于**回归验证**，确认没被本次改动破坏
